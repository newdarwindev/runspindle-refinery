# Linux-native preparation candidate

Status: independently reviewed preparation candidate only. This proposal does
**not** replace `offline/dependencies.json`, alter launcher gates, qualify DSPy,
or authorize providers, deployment or promotion. It advances #16 without closing it.

## Why a separate candidate

Read-only forensic reconstruction recovered all 11,801 historical canonical byte
hashes, including every RECORD and generated script. The 20 historical scripts
encode a Mac Python 3.12 interpreter path, despite the Linux ARM64 Python 3.14
package target. The original cross-platform install recipe did not pin its
preparation interpreter. Byte recovery does not make those scripts valid Linux
launchers or prove a uniquely identified historical installer version.

The strict current preparation recipe correctly requires
`/usr/local/bin/python3.14`. Its generated scripts cannot simultaneously match
that historical inventory. Do not rewrite existing evidence or call a new
inventory the original preparation.

## Explicit new candidate

`offline/linux-native-candidate/` retains the actual new inventory, strict
preparation recipe, wheelhouse provenance and sanitized receipt. No third-party
package or interpreter payload is committed. Existing dependency licenses,
notices and metadata records remain identical to the historical inventory.

Preparation used the existing exact Python 3.14.0 Linux ARM64 image and verified
uv 0.13.6 ARM64 binary, with no NIC and container network disabled. All 76 exact
locked wheels were retained, selecting native CPython 3.14 ARM64 wheels rather
than pure-Python alternatives where the original inventory used extensions.
No provider or model was called; no prepared dependency was imported.

The wheels reside on a sealed read-only UDF filesystem image, SHA256
`241dc8e276f8c3f3e5395f9b853edcd13e690439f1a50bde5f036e1937a69671`.
The image is retained as an operator artifact, not distributed by this PR.
A changed or unavailable artifact blocks reproducing this receipt; reconstructing
a different UDF from the same wheel bytes is not equivalent evidence.

This matters because uv records local artifact Unix ctime in `uv_cache.json`.
Copying the wheel files into a new filesystem can change preparation bytes.
The recipe mounts the identical sealed filesystem read-only at `/wheels`, with
readable directory permissions, preserving its metadata. Do not strip installer
metadata or rewrite RECORD files to make candidates compare equal.

Two separate fresh Linux ARM64 guest roots prepared and audited the candidate.
Full candidate JSON and all wheel hash/ctime/mode observations matched. Both
cleanly stopped for review. This proves reproduction **from the same sealed
wheelhouse**, not reproducible construction of the UDF itself.

The new inventory has 11,877 files. Relative to historical canonical:

- 76 added, retained `uv_cache.json` installer metadata files;
- 76 changed RECORD files accounting for actual generated bytes;
- 20 changed scripts with the actual Linux Python 3.14 interpreter;
- no missing files, package version changes, license or notice changes.

Candidate manifest canonical-JSON SHA256:
`2f439085e18c57e109144d40bb8eab300597d88de6127fad13afc218590fdc1f`.
This digest is for canonical JSON serialization, not pretty-printed file bytes.

## Remaining approval and verification gates

1. Review this explicit candidate and the retained wheelhouse artifact/distribution
   mechanism. This PR alone does not adopt it as canonical.
2. If adopted in a separate reviewed change, preserve historical evidence and
   bind the launcher to the exact new inventory, image, recipe and artifact.
3. Execute the actual optimizer twice only after the exact new integrity gate
   is intentionally enabled; retain identical reports and negative tests.
4. Keep provider/live qualification separate. Preparation is not optimizer
   execution, production readiness or quality evidence.

Repository tests here check candidate/receipt integrity and the bounded delta;
they do not import DSPy or replay native guest preparation.
